## Feedback

### For the planner

- **"The codec's `parse` spec is the same object the single-command bin uses" cannot mean instance identity, and the plan should say so.** A commander `Command` has exactly one `parent`: `addCommand` overwrites it. Two calls to `buildParseCommand()` therefore yield two instances by necessity, and memoizing the builder to make them identical would break `art-parse parse` and `art-codec parse` in the same process. The tests assert what the intent can actually be — the two specs produce identical help output (modulo the `Usage:` prefix, which carries the owning program's name), and each command's `parent` is its own program. If object identity was intended, the plan needs a way to express it that commander supports.
- **Nothing in the plan sets a non-zero exit code on failure, and the plan's own integration test expects one.** The plan's `cli/bin/src/bin/cliIntegration.test.ts` bullet asserts "the non-zero exit on a parse failure", but `doParse`/`doSerialize` catch, log, and answer `null`, and no step — here or in the three previous iterations — tells the action or the entry point to set `process.exitCode`. Measured through `vite-node`: `art-serialize /tmp/nonexistent.json` logs `🔴 | serialize | …` and exits `0`. `verify-bin-coverage` will fail on its first run for this reason; one line in the action (or a `finally` in the entry point) closes it.
- **Operation lines land on stdout and corrupt piped output.** `createLogger` writes with `console.info`, and `quiet` still logs resolved operations, so `art-parse --json > doc.json` writes `🟢 | parse | - | (4ms)` ahead of the JSON and `art-serialize` then rejects it with `Unexpected token`. The `--write` route roundtrips cleanly; the piped route cannot. This is now reachable because of this iteration, and no step owns it — either the logger moves to stderr, or stdout data output suppresses the log. The plan should decide which, and in which iteration.
- **`--json` is still absent from `serialize`, so the roundtrip is one-directional.** Carried over unchanged from the parse and serialise reports: `doSerialize` accepts and honours `json` through `presentContent`, but nothing exposes it. The serialise command can consume a JSON document and cannot produce one, so `art-parse --json | art-serialize` has no counterpart form to pair with. The instruction followed the plan literally (`[file]`, `-o`, `-w`); the plan should either add the option or drop `json` from `SerializeOptions`.
- **The built bundle cannot be executed by plain `node` in this workspace, which blocks the planned integration test.** `node dist/esm/bin/codec.mjs --help` fails with `ERR_MODULE_NOT_FOUND` for `libs/codec/src/createArtCodec` imported from `libs/codec/src/index.ts`: `@art-md/codec`'s manifest sets `"main": "./src/index.ts"` and the workspace symlinks resolve to sources, so the externalized dependency never loads as ESM. Pre-existing and untouched here, but `cliIntegration.test.ts` spawns exactly those bundles, so `verify-bin-coverage` needs either published `exports` for the libs or a bundling change that stops externalizing workspace packages.
