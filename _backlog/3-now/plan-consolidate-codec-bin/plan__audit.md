## Ambiguities and Conflicts

Decisions needed before the refactoring iteration; each affects the size of the refactor.

1. **Constants in `types.ts` vs `constants.ts`** — the convention text and its example place exported constants in `types.ts`, but the package (and repo) idiom is dedicated `constants.ts` files (8 files). Decide: merge into `types.ts`, or accept `constants.ts` as an equivalent location and amend the convention.
2. **Fixture factory naming** — `make{Construct}Mock` read literally renames every `make*Fixture` factory (6 files) to `...Mock`, colliding with mock vocabulary and with the existing `makeCodecMock`. Decide the intended naming (`make{Construct}Fixture` amendment vs literal rename).
3. **Context mock naming conflict** — Function Mock Naming and Context Mock Naming prescribe different names for `createCommandContextMock`; pick the governing rule.
4. **No Multi-Line Nested Declarations, strict reading** — ~70 sites (object/array literal args and nested calls), overwhelmingly in tests where `expect(...).toHaveBeenCalledWith({...})` requires literal arguments. Decide enforcement scope: production only? exempt matcher arguments? This is the single largest refactor lever.
5. **`new Date()` inside literals** — decide whether `new` expressions count as "function calls" for the No Function Calls in Literals rule (~10 sites in operation factories, fixtures, and tests).
6. **Entry scripts vs File as Function** — `bin/codec.ts`, `bin/parse.ts`, `bin/serialize.ts` are shebang scripts with no function; decide exemption, or extract a shared run function (which also removes the triplicated load-config → build-program → parse sequence).
7. **Type-guard naming** — decide whether `validateVerbosity` must gain an `is`/`has`/`should`/`can` prefix or the boolean-naming rule admits `validate`-style type guards.

## Observations (outside convention scope)

Not convention violations; recorded because they affect the refactoring iteration.

1. The `parse` and `serialize` paths are parallel duplicates (command factories, `do*` bodies, option wiring) — already tracked by the plan's duplication scope.
2. No unit tests exist for `bin/commands/{parse,serialize}/create*Command.ts`, `bin/options/*`, `logger/createConsoleWriter.ts`, `logger/validateVerbosity.ts`, or the entry scripts; refactoring them has no suite guard.
3. Type-assertion escapes hide mismatches: `return action as CommandHandler` (`createParseCommand.ts:29`, `createSerializeCommand.ts:29`), `as unknown as ArtCodec` (`makeCodecMock.ts:8`), `as unknown as typeof process.stdout.write` (`writeOutput.test.ts:24`, `writeStdout.test.ts:15`), `JSON.parse(source) as ArtDocument` (`doSerialize.ts:28`).
4. Import style is inconsistent: `import { type LoggerAPI }` (`createCommandContext.ts:4`) vs `import type` elsewhere; `createOperationsLogMock.ts:3` imports types from `createOperationsLog.ts` instead of `operations/types.ts`.
