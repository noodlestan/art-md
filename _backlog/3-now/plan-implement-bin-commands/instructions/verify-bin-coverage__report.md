## Feedback

### For the planner

- **The built bundles still cannot be run by plain `node`, and the test now works around it with a bespoke resolver.** The integration test would otherwise be impossible, so the workaround shipped, but it must not be mistaken for the bundle being fixed. `@art-md/codec`'s manifest sets `"main": "./src/index.ts"` and the sources use extensionless relative imports, so `node dist/esm/bin/codec.mjs` fails with `ERR_MODULE_NOT_FOUND` on `libs/codec/src/createArtCodec`. The preloader maps `@art-md/*` onto `libs/*/src` and lets Node's type stripping do the rest. Two fixes were tried and rejected before the shim: (a) publishing `exports` for the libs, which is a separate change and out of scope here, and (b) bundling the workspace dependencies into the bin's esbuild output, where `esbuild-plugin-file-path-extensions` marks cross-root imports external and rewrites them to relative `.mjs` paths that do not exist. Pointing the shim at the libs' `dist` instead of their `src` does not work either — `libs/codec/dist/esm` is browser-targeted and its decoder entry calls `document.createElement`. **This needs its own task.** The plan should decide whether the fix is published `exports` or a workspace-aware bundling rule, and this instruction's test should be revisited once it lands.
- **Both of the failures the previous report predicted are fixed, but the plan never assigned them.** They were delivered here as findings rather than as planned steps, which is fine, but the plan should now fold them into the `## Goals` table so a future re-read does not rediscover them.
- **`--json` is still absent from `serialize`, carried over unchanged.** `doSerialize` accepts and honours `json` through `presentContent` and nothing exposes it, so `art-parse --json | art-serialize` works only because serialize does not need the option. This was raised in two previous reports and remains open; the plan should either add the option or drop `json` from `SerializeOptions`.
- **The instruction said the integration test must spawn plain `node`, and it does not.** Each child is `node --import <data: url>`. The plain invocation is what fails today, so the plan should either relax the wording or accept that the test asserts the bundle's behaviour, not the package's installability. What the test genuinely does not cover is `npm pack` → install → run, which is where the packaging defect would actually bite a consumer.

### For the technical writers

- **`cli/bin/README.md` is still contradicted by the code**, as reported by the previous iteration and not fixed here: it says the command behaviour is not yet implemented, that the package's export surface is types only, and — implicitly — that no operation logging exists. All three were falsified two iterations ago.
- **`cli/bin/_guide.md` Package Layout does not mention `src/private/commander/`, `src/private/operations/`, `src/private/present/`, `src/private/logger/`, or the new `src/test/helpers/`**, and still closes by saying the behaviour behind `src/bin/` is still to land. `src/test/helpers/` is new this iteration and holds the two files whose whole purpose is making the bundles loadable in tests, so it deserves a line.
- **Nothing about the new test helpers is documented anywhere.** `spawnCli.ts` deliberately throws a `run npm run build` hint when the bundles are missing instead of skipping, which means `npm run test` fails on a clean checkout until the package has been built once. That ordering is safe today only because `ci` runs `build` before `test:ci`; a contributor running `npm run test` directly will hit it. Worth one line in `_guide.md`.
- **The `Serialize` versus "serialise" spelling split is now encoded in tests**, in the same way the previous iteration warned about: the module, type, and function names are `Serialize`, the README says "serialise", and `cliIntegration.test.ts` asserts `art-serialize serialize`. If the canonical wording is ever fixed, that test and `types.ts` have to move together.

### For the crew

- **`module.registerHooks` is the cheapest way to make a workspace-sourced bundle runnable**, and it needs Node ≥ 22.15 — `package.json` only requires `>=22`, and `registerHooks` is used in a synchronous hook, which is what lets it return `shortCircuit: true`. A sync `try`/`catch` around `nextResolve` is the whole trick for catching `ERR_MODULE_NOT_FOUND` and `ERR_UNSUPPORTED_DIR_IMPORT`, since Node's own resolver throws rather than returning a nullish result there.
- **`spawnCli` needs no build integration of its own.** Precompiling the preloader from the same `src` tree the bundle comes from is enough; a `data:text/javascript` URL carrying `import { registerWorkspaceLibraries } from "file://…"` avoids a second `node_modules` fixture. `existsSync` on both the bundle and the resolver bundle gives the "build first" error instead of an opaque `ENOENT` from `spawn`.
- **Asserting `process.exitCode` in vitest leaks across files unless it is restored.** Both command test files now clear it in `afterEach`, and the exit-code helper's own tests do the same; without that, a failing assertion in one file can flip the exit status of an unrelated worker.
- **Switching a logger from stdout to stderr is a one-line change with a wide test tail**, but only because the logger had exactly one caller-facing dependency: `createLogger.test.ts` and `createCommandContext.test.ts` both spied on `console.info`, and those two files were the entire blast radius. The integration test is what proves it matters — the `--json` pipe roundtrip is the only assertion that would have caught the original defect.
- **Coverage thresholds that a test file cannot see are worth naming in the report.** `registerWorkspaceLibraries.ts` is 96 lines of real branching logic with no v8 coverage at all, because it only ever runs inside the spawned child. That is acceptable for a test harness, but it is invisible in the coverage summary, and `spawnCli.ts` shows up at 75% branches for the same reason.
